# 把 MCP 工具从每一轮提示词里挪出去

> 一次实测：两个 MCP 服务、21 个工具，每轮固定花掉约 5.7k token。改造后归零，调用体验不变。

## 问题不是「工具太多」

模型能看见的工具定义，是要付租金的：每轮请求都带着一遍。

接两个 MCP 服务，实测：

| 服务 | 工具数 | schema 与描述 | 折算 token |
|---|---|---|---|
| 桌面操控 | 11 | 9067 字符 | 3022 |
| 芯片配置工具 | 10 | 8206 字符 | 2735 |

这不是「要不要精选工具」的问题。工具越少，省的那点租金抵不过砍掉的能力；
而只要服务数量继续长，这条曲线就是线性的。

## 常见的第一反应：分类

很容易写出这样一张表：

| 服务类型 | 形态 |
|---|---|
| 有状态（跨调用攒数据） | 注册进工具列表 |
| 无状态（每次自带全部输入） | 按需调用 |

它是对的，但每接一个新服务都要重新判断一次，规则随服务数增长。判断本身成了负担。

## 换一个轴：有没有一个活着的进程

有状态的服务之所以必须常驻，是因为它的状态在进程内存里。既然如此，让它常驻的
可以是进程，不必是提示词。

做法：一个常驻代理进程把 stdio 服务挂在回环端口上，命令行每次只是连上去调一个工具。
进程活着，状态就在；提示词里一条工具定义都没有。

```
命令行 ──HTTP──> 代理(常驻) ──stdio──> MCP 服务(常驻)
```

验证这个设计的那个测试很简单：在被测服务里放一个进程内自增计数器。

| 调用方式 | 第一次 | 第二次 | 第三次 |
|---|---|---|---|
| 每次起新进程 | 1 | 1 | 1 |
| 经代理 | 1 | 2 | 3 |

## 统一接口长什么样

一个配置文件 + 一个命令，所有服务一视同仁：

```yaml
servers:
  some-service:
    command: /path/to/server
    args: [serve]
    port: 8941
    ttl: 900
```

```text
mcp-call servers                      # 有哪些服务，哪个在跑
mcp-call tools  --server X            # 先看有什么工具
mcp-call call   --server X --tool T --kv k=v
mcp-call session --server X --steps @steps.json   # 一次启动跑一串
mcp-call close --all
```

几个值得抄的细节：

- **参数三种给法**：`--kv` 给扁平值，`--args @file` 给嵌套结构，`--stdin` 读管道。
  命令行里手写 JSON 十次有两次被引号吃掉。
- **状态文件只是缓存**：端口上已经有服务在应答就接管它，不报错。丢了状态文件不该需要人工清理。
- **孤儿进程要扫**：`taskkill /T` 顺着父进程杀，代理隔出来的孙进程有时漏网，
  按命令行特征再扫一遍。
- **失败要说人话**：工具超时不要抛一坨异步异常组，直接说「没在 N 秒内回应，加大 --timeout 或者确认它真的需要这么久」。

## 代价

| 项 | 说明 |
|---|---|
| 多一层进程 | 需要 TTL 回收与 `close --all` 兜底 |
| 多一次往返 | 第一次要 `tools` 看参数，之后直接调 |
| 只适合单机 | 回环地址、无认证，多用户场景不适用 |

## 什么时候还是该注册

如果某个工具是每轮都要反复用的基础能力（读写文件、跑命令这种），让它常驻仍有价值：
少一次命令行往返，模型也不容易忘记。

判断标准从「服务有没有状态」换成「这东西是不是每轮都动」。
