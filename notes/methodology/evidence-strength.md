# 证据强度阶梯

写于 2026-09-21 · 与 [Verification Before Completion](./verification-before-completion.md) 配套

---

## 这篇解决什么问题

[Verification Before Completion](./verification-before-completion.md) 给的是**纪律**：
不许在没有新鲜验证证据的情况下宣称完成（Iron Law / Gate Function）。

但它没回答一个更容易出错的问题：**什么样的证据才算证据？**

「我验证过了」这句话可以是完全诚实的，同时结论完全错误 ——
因为拿到的证据只够证明一个弱命题，却被当成了强命题的证据。
这篇给一个可操作的排序标准。

---

## 核心判据

> **证据强度 = 它与最终产物的距离。**

离最终产物越近，证据越强；离得越远，越接近猜测。
「最终产物」指用户真正要的那个结果本身 —— 不是它的前置条件、不是它的中间状态、不是关于它的报告。

---

## 阶梯

| 级 | 证据类型 | 例 | 能支撑的声明 |
|---|---|---|---|
| **L0** | **真实产物**：真跑一次目标动作，拿到真实返回 | 真调一次工具、真实请求返回预期数据、真实用户操作走通 | ✅ 可以宣称完成 |
| **L1** | **全量验证命令的完整输出 + 退出码** | 测试全跑完看到 `0 failed`；构建 exit 0 | ✅ 可以宣称完成（限该命令覆盖的范围）|
| **L2** | **干跑 / 子集 / 间接运行** | `--dry-run`、只跑相关测试子集、静态检查通过 | ⚠️ 只能说「未发现问题」，不能说「可用」 |
| **L3** | **中间信号** | 进程起来了、日志打了 `started`、文件被创建、端口在监听 | ❌ 只能说「有人拉起了它」 |
| **L4** | **静态推断** | 读代码/配置觉得「应该能跑」 | ❌ 是假设，不是证据 |
| **L5** | **他者自述** | agent 汇报成功、commit message 说修好了、文档写着已支持 | ❌ 待验证的输入，不是结论 |

**只有 L0 和 L1 能支撑「完成」。** L2 及以下全是「还没失败」，不是「已经成功」。
两者差别在于：前者只说明搜索空间还没被走完。

---

## L3 为什么最危险

L4/L5 大多数人会本能地保持怀疑。L3 不会 —— 它**看起来像运行证据**，
有进程、有日志、有时间戳，感官上跟 L1 很像。三个具体失真模式：

### 1. 存在性 ≠ 可用性

进程出现只说明**有人拉起了它**，不说明**链路可用**。
拉起成功和握手成功是两个独立的失败点，前者通过不蕴含后者通过。

> 实例：给一个 harness 接入外部工具服务后，服务进程确实被拉起了（时间戳、路径都对）。
> 但配置里目标那一行实际没生效 —— 最终是靠**真调一次工具拿到真实返回**才确认链路通的。
> 只看进程，会得出相反的结论。

### 2. 静默跳过：警告 ≠ 报错

`exit 0` 是**整个命令**的退出码，不是**每一步都做了**的证明。
一个只 `warn` 不 `error` 的框架，会在什么都没做的情况下返回成功。

> 实例：配置校验命令 exit 0、stderr 里没有任何 `error`。
> 但输出里藏着一句不起眼的 `entry not found` —— 那一步被跳过了，配置根本没生效。
> **判定「成功」时必须同时看：退出码 + 完整输出 + 有没有 warning。**

### 3. 成功路径 ≠ 目标路径

命令成功了，但做的是另一件事。典型来源：默认参数、缓存、回退分支、同名不同物。
判据是「**你验证的是不是你声称的那个东西**」，而不是「有没有成功」。

## 可操作用法

### 反问一句就能定级

> 「哪个命令的输出，能**证伪**这条声明？」

- 说不出来 → 这不是证据，是感觉（L4/L5）
- 说得出，但那个命令只是**启动**了什么 → L3
- 说得出，命令跑到最后并给出产物 → L1
- 那个「命令」就是用户要的动作本身 → L0

### 组合证据的规则

1. **一层一类证据**。L3 通过不能推出 L1，L1 通过不能推出 L0 —— 不同层要分别取证。
2. **取最强的那一层下结论**。链条里最弱的一环决定结论强度。
3. **声明和证据必须同级**。
   - 「配置已写入」→ L1 够了（文件确实写进去了）
   - 「配置已生效」→ 必须 L0（真跑一次，看行为变了）

### 最容易混的一对

| 声明 | 需要的级 | 常见误用 |
|---|---|---|
| 我做了 X | L1（X 的产物存在）| 用「我运行了做 X 的命令」代替 |
| X 起作用了 | **L0**（可观察到的行为变化）| 用「X 的产物存在」代替 |

**「已落盘」和「已生效」是两个声明，不是一个。**

## 与 Common Failures 对照表的衔接

[Verification Before Completion](./verification-before-completion.md) 里那张表列了常见谎言，
补上 L3 这一行之后是完整的：

| 声明 | 需要 | 不足以支撑 |
|---|---|---|
| 测试通过 | 测试命令输出 0 失败 | 上次的运行结果、「应该能过」 |
| Lint 干净 | Lint 输出 0 错误 | 部分检查、外推 |
| 构建成功 | 构建命令 exit 0 | Lint 通过、日志看着正常 |
| Bug 已修 | 复现原症状的测试通过 | 改了代码、假定修好了 |
| Agent 完成 | VCS diff 确有改动 | agent 自述「成功」 |
| 需求满足 | 逐条核对清单 | 测试通过 |
| **服务已接入**（补） | **真调一次、拿到真实返回** | **进程起来了 / 端口在监听 / 日志打了 started** |
| **配置已生效**（补） | **行为可观察地变了** | **文件已写入 / 校验命令 exit 0** |

## 一页速查

```
宣称完成前，问三件事：

1. 我的证据在第几级？           L0/L1 → 可以下结论；L2 以下 → 只能报「未发现问题」
2. 声明和证据同级吗？           「已落盘」≠「已生效」，差一级
3. 完整输出看了吗？            exit 0 + 无 error ≠ 没跳过；warning 要单独查

判据一句话：
  完成状态的证据必须落在最终产物上，不能是中间信号。
```
